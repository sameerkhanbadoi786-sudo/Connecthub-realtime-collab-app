# ConnectHub — Real-Time Communication & Collaboration App

A video conferencing + collaboration web app: multi-user video calls, screen
sharing, a shared whiteboard, file sharing, and JWT-based authentication.

## Features

| Feature | How it's implemented |
|---|---|
| Multi-user video calling | WebRTC full-mesh (`RTCPeerConnection` per peer) |
| Screen sharing | `getDisplayMedia()` + `replaceTrack()` on existing peer connections |
| Whiteboard | HTML5 Canvas, strokes broadcast over Socket.io and replayed for anyone who joins mid-session |
| File sharing | REST upload (`multer`) + Socket.io broadcast of file metadata |
| Chat | Real-time messaging with emoji picker and @mention autocomplete/highlighting |
| Auth | bcrypt password hashing + JWT sessions |
| Encryption | HTTPS/WSS (self-signed for local dev, real cert in prod), bcrypt at rest, DTLS-SRTP for all WebRTC media (built into the WebRTC spec) |
| Real-time signaling | Socket.io (also relays WebRTC offer/answer/ICE candidates) |

## Design

The UI follows an "on-air / broadcast" visual language rather than a generic
dark SaaS theme: graphite base (`#14161B`), amber accent (`#E8A33D`) reserved
strictly for *live* states (active mic, active speaker, primary actions),
Space Grotesk for headings/labels and Inter for body/UI text. The ring
around a video tile isn't decorative — it's driven by real-time audio-level
detection (Web Audio API `AnalyserNode`) on that peer's actual stream, so it
lights up only while someone is actually speaking.

## Project structure

```
realtime-collab-app/
├── server/
│   ├── server.js       # Express app + Socket.io signaling server (HTTPS if certs/ exists)
│   ├── auth.js         # /api/auth/register, /login, /verify
│   ├── middleware.js    # JWT route guard
│   ├── db.js            # SQLite user store (Node's built-in node:sqlite)
│   ├── users.db          # created automatically on first run
│   ├── uploads/          # uploaded files land here
│   ├── certs/            # generated by `npm run certs` (gitignored, not included)
│   ├── scripts/
│   │   └── generate-certs.js  # creates a local self-signed TLS cert
│   ├── .env.example      # copy to .env for JWT_SECRET / NODE_ENV / PORT
│   └── package.json
└── public/
    ├── index.html        # login / register screen
    ├── lobby.html         # "create or join a room" screen (new)
    ├── room.html          # call + whiteboard + files + chat UI
    ├── css/style.css
    └── js/
        ├── auth.js        # login/register logic → redirects to lobby.html
        ├── lobby.js        # create room / join room / logout logic
        ├── room.js         # WebRTC mesh, screen share, controls, files, chat
        └── whiteboard.js   # canvas drawing + sync
```

**Flow:** `index.html` (not signed in) → sign in or register → `lobby.html`
(pick **Create a Room** or enter a code to **Join a Room**) → `room.html`
(the actual call). Leaving a call returns you to `lobby.html`; logging out
returns you to `index.html`.

## Running it locally

```bash
cd server
npm install
npm start
```

Then open **http://localhost:3000** (or **https://localhost:3000** if you
generated certs — see below) in two different browser tabs (or two devices
on the same network) to simulate multiple participants:

1. Register two different accounts (one per tab/device).
2. You'll land on the lobby screen. On one tab, click **Create a Room** —
   this generates a room code and takes you into `room.html?room=xxxxx`.
3. Copy that URL (use the **Copy Link** button in the room header) and open
   it in the second tab/device — or just have the second account click
   **Join a Room** on their lobby screen and type the code in.
4. You should see both video feeds, be able to share your screen, draw on
   the whiteboard together, and share files.

> Camera/mic access requires either `localhost` or HTTPS — browsers block
> `getUserMedia`/`getDisplayMedia` on plain HTTP for any host other than
> localhost. See "Deploying" below for enabling HTTPS.

## Running it over HTTPS/WSS locally (optional but recommended)

By default the server runs over plain HTTP/WS, which is fine for `localhost`
testing (browsers exempt `localhost` from the HTTPS requirement for
camera/mic access) but means the page itself, the JWT, and the Socket.io
connection aren't encrypted in transit. To turn that on locally:

```bash
cd server
npm install
npm run certs   # generates a self-signed cert into server/certs/
npm start
```

The server auto-detects `server/certs/key.pem` + `cert.pem` and switches to
HTTPS/WSS automatically — you'll see `Server running: https://localhost:3000`
in the console instead of `http://`. Your browser will show a "not secure" /
"self-signed certificate" warning the first time — that's expected, click
through it (e.g. "Advanced → Proceed to localhost"). This is a dev
convenience only; real deployments should use a certificate from an actual
CA (see "Security notes" below), not this self-signed one.

## How the pieces fit together

- **Signaling vs. media are separate.** Socket.io only ever carries small
  JSON messages (who joined, WebRTC offers/answers/ICE candidates, whiteboard
  strokes, chat, file metadata). The actual audio/video/screen bytes flow
  **peer-to-peer** directly between browsers over WebRTC — the server never
  sees or touches raw media.
- **Full-mesh topology.** Every participant opens a direct `RTCPeerConnection`
  to every other participant. This is simple and reliable for small rooms
  (~2-6 people). Beyond that, each client is uploading its stream N-1 times,
  which doesn't scale — see "Next steps" below.
- **Auth guards both REST and sockets.** The JWT issued at login is sent (a)
  as a `Bearer` header for REST calls like `/api/upload`, and (b) in the
  Socket.io handshake (`auth: { token }`), so only signed-in users can join a
  room or open a socket connection at all.

## Security notes

- Passwords are hashed with bcrypt (10 salt rounds) — never stored or logged
  in plain text.
- Auth uses signed, expiring JWTs (12h) rather than server-side sessions.
- The `/api/upload` route and all room-joining socket events require a valid
  token.
- WebRTC media is encrypted end-to-end via DTLS-SRTP by spec — this is true
  regardless of anything this server does.
- **The server now enforces one thing automatically:** if you set
  `NODE_ENV=production` without also setting a `JWT_SECRET` env var, the
  server refuses to start rather than silently signing tokens with the
  hardcoded dev secret. Locally (no `NODE_ENV=production`), the dev fallback
  still works so you don't need a `.env` file just to run `npm start`.
- **For production you must additionally:**
  1. Serve everything over HTTPS/WSS using a certificate from a real CA
     (Let's Encrypt, or a reverse proxy/host like Nginx, Caddy, Render,
     Railway, etc. that terminates TLS for you). The self-signed cert from
     `npm run certs` is for local dev only — don't ship it.
  2. Set `NODE_ENV=production` and a strong, random `JWT_SECRET`
     (`openssl rand -hex 32`) via your real secrets manager, not a committed
     file.
  3. Add a TURN server alongside STUN — some users are behind NATs/firewalls
     that STUN alone can't traverse, and without TURN those users simply
     won't be able to connect to anyone else in the room. Set `TURN_URL`
     (e.g. `turn:turn.example.com:3478`), `TURN_USERNAME`, and
     `TURN_CREDENTIAL` in `.env` — the server exposes them to the client at
     runtime via the authenticated `/api/ice-config` endpoint, so no
     credentials are hardcoded into the public JS. Options:
     - Self-host [coturn](https://github.com/coturn/coturn) (a Docker image
       is the fastest way to get one running).
     - Use a managed TURN provider (Twilio Network Traversal Service,
       Metered, Cloudflare Calls, etc.) and drop their credentials into the
       same three env vars.
  4. `db.js` now uses SQLite (Node's built-in `node:sqlite`, available since
     Node 22.5+, WAL mode) instead of a raw JSON file, so concurrent
     registrations can't race and corrupt the store, and a unique index
     enforces one account per username at the DB level. It's the
     zero-dependency option (no native build step, so nothing to compile on
     Windows/Mac/Linux) but Node still labels it "experimental" and may log
     a warning on startup — that's expected and harmless. `users.db` is
     still a single file on local disk, though — for
     multi-instance deployments (more than one server process/container),
     move to a real client-server DB (Postgres, MySQL) so all instances
     share one store. Uploaded files and `users.db` currently sit
     unencrypted on disk (passwords inside are still hashed); disk/volume
     encryption or a managed DB with encryption-at-rest closes that gap.
     If you're upgrading from an older version of this project that used
     `users.json`, the server migrates it into `users.db` automatically the
     first time it starts and renames the old file to `users.json.migrated`.
  5. Set `CORS_ORIGIN` in `.env` to your real frontend URL(s) — it's applied
     to both the Express API and the Socket.io handshake. Leaving it unset
     defaults to `*` (any origin), which is fine for local dev only: in
     production it lets any website make requests against this API using a
     visitor's browser, using whatever token that visitor already has.
  6. Login and registration are rate-limited (20 requests / 15 min / IP) to
     slow down password brute-forcing and username enumeration. Tune the
     limit in `server.js` (`authLimiter`) if it's too strict or too loose
     for your traffic.


## Next steps / stretch goals

- Swap the full-mesh WebRTC topology for an **SFU** (mediasoup, LiveKit,
  Janus) to support larger rooms efficiently.
- Persist the whiteboard beyond the life of the meeting (currently it's
  shared with everyone for the duration of a session, including latecomers,
  but is cleared once the room empties) — e.g. save it to the DB so it can
  be reloaded or exported as an image/PDF later.
- Add room passwords / invite-only rooms, and a "waiting room" / host
  approval flow.
- Add recording (MediaRecorder API) with server-side storage.
- Move from single-file SQLite to Postgres/MySQL if this ever needs to run
  as more than one server instance (SQLite is one file, shared by exactly
  one process).
